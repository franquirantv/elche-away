# Proposed architecture

Production delivery: [CD](CD.md) defines the owner-authorized automatic recovery → migration → Vercel deployment → smoke pipeline, initially disabled pending external configuration. GitHub Actions is the sole Production deployer; Vercel Git integration retains Preview only (`main` auto-deploy is disabled in `vercel.json`). Application builds do not run migrations. PostgreSQL recovery branches remain isolated from development, testing and Preview.

Status: Foundation is implemented with Next.js, React, strict TypeScript and Tailwind; Milestone 2 adds PostgreSQL/Drizzle read-only trips and stadiums; Milestone 3 auth/reference editing is complete; Milestone 4a adds local fixture and attendance administration; Milestone 4c adds explicit static-file imports; deployment remains planned. Product scope lives in PRODUCT; relational rules live in DATABASE. The owner configured nonproduction Neon development/testing branches; no production or deployment has been provisioned.

## One application

Keep Next.js App Router, TypeScript, Tailwind, Neon PostgreSQL, Drizzle and Vercel. One deployment handles public rendering and private editing. A real relational database fits repeated visits and independent venues; SQLite would reduce services locally but complicate durable writes on the chosen serverless host. No separate backend, GraphQL, Redis, queue, search service or Docker requirement.

Use Node runtime. Server Components call narrow server-only query functions directly, without fetching the application's own HTTP endpoints. Client Components handle only interaction such as the map. Server Actions handle forms; Route Handlers exist only for required HTTP integrations such as OAuth callbacks. Validate input and authorize each protected server entry point. Public query functions return only display fields and require attendance when selecting trips, visited stadiums, markers or personal statistics. Unattended fixtures stay admin-only. Keep domain calculations outside React components.

Proposed structure (create only as features need it):

```text
src/app/(public)/           home, trips/[slug], stadiums/[slug], map
src/app/admin/              protected pages, colocated forms/actions
src/components/             genuinely shared UI
src/db/                     server-only client, schema, focused queries
src/server/                 auth, authorized operations, validation
src/lib/                    pure domain calculations and geography mapping
drizzle/                   reviewed SQL migrations (at repository root)
tests/                     meaningful cross-feature/integration checks
```

Initially use explicit request-time public reads and uncached admin reads. Avoid accidental database-dependent build prerendering. Successful writes must appear on subsequent reads; introduce caching/revalidation only when needed. No generic repository/service interfaces or global client state framework.

## Public URLs and identity

Use `/` for the map-first public experience. `/?view=trips`, `/?view=stadiums` and `/?view=summary` open lists and the existing attendance summary; `/?stadium=<slug>` and `/?trip=<slug>` open resource panels. `/map` redirects to `/`, preserving query parameters. Preserve `/trips`, `/trips/[slug]`, `/stadiums` and `/stadiums/[slug]` as redirects to the corresponding map view/panel, retaining the original slugs. Public content has no standalone document-page alternative. Invalid/ambiguous selections and missing or nonpublic resources return 404. Keep English route segments despite Spanish public labels. UUIDs remain internal identity and foreign keys. No public club detail route is required. See [MAP_EXPERIENCE](MAP_EXPERIENCE.md).

The home Server Component resolves the URL selection and queries only PostgreSQL public attendance-based functions. Marker data stays minimal; trip lists/details are rendered on the server only when requested. A small client shell owns the nonmodal panel's mobile expansion, focus, Escape handling and marker navigation. Leaflet receives stable geographic props across query transitions, preserving its instance and viewport; selecting a located resource reveals its marker. Native Next.js query navigation supports direct entry, reload, back/forward and progressive enhancement without a separate API or global state framework. Panel state is the URL; map pan/zoom and panel expansion are local transient state. `TripFacts` and `TripList` render the panel content. A small path-aware `AppShell` changes presentation only: `/admin` and `/auth/*` retain the document header, footer and container; public routes render a fixed viewport map with floating controls. This does not authorize any private operation. Zoom, four directional pan buttons and reset-to-peninsula operate directly on Leaflet. Reset closes the selected panel. Coverage, personal-archive disclosure and the admin link live in a native disclosure over the map.

Generate slugs once, resolve collisions under a database unique constraint, and never regenerate them on edits. Date/opponent corrections and stadium renames preserve URLs. No slug editor/history/redirect infrastructure in MVP. DATABASE owns the exact slug policy. Admin mutations use UUIDs and still authorize and validate all input; readable URLs are not access control.

Club crest uploads now use approved Neon Object Storage (Milestone 5), with object keys in PostgreSQL and a neutral fallback. Legacy local references remain only for additive upgrade/rollback. Core branding must not depend on the Elche crest or other copyrighted visuals. Matches hold fixture facts; attendance is an optional one-to-one personal record, exposed publicly as a trip. Attendance → TripPhoto is one-to-many; its table and photo upload/gallery remain post-MVP.

## Fixture import boundary

PostgreSQL is the runtime source of truth. Neither public rendering nor normal admin browsing calls a football provider. Keep file parsing and source-to-local mapping behind the protected import boundary; database reconciliation belongs in src/db. No football-provider credentials are needed; GitHub acquisition is restricted to explicit protected import checks. Convert responses into typed local fixture inputs and use the same domain validation as manual writes. Do not create a provider abstraction framework before comparing an actual provider; contain its client and mappings so replacement does not alter public components or domain identity.

Implemented 4c flow: the authenticated owner requests a season range from OpenFootball, reviews a global preview including proposed references and confirms bounded transactional batches. Local JSON/Football.TXT upload remains an advanced fallback. Only an explicit authorized direct-import check fetches OpenFootball; normal public/admin reads never do. Validate provider data as untrusted input, keep credentials out of the browser/logs, and return sanitized preview data. Reauthorize and validate the apply request server-side; a browser preview is not trusted write authority. Use explicit offsets over the uploaded file and bounded chunks within deployment limits; a failed batch rolls back completely and can be retried through persistent version mappings. No cron, webhook, queue, worker or live-result integration. Do not store raw payloads by default.

DATABASE owns deduplication and correction rules: source identity first, conservative candidate reconciliation for new IDs, transactional apply, and whole-fixture facts_locked protection after a manual correction. Sync cannot mutate attendance, personal notes, special status, slugs or photo records. A missing provider record is never a deletion instruction. External identifiers are opaque mappings, not local identity. Keep old mappings when providers/IDs change. Source errors leave the archive unchanged and usable.

Provider research is a separate milestone comparing Primera, Segunda, Primera Federación/historical lower tiers, Copa del Rey, playoff coverage, history from approximately 2018, dates/scores/teams/stadiums, rate/free-tier limits, and licensing for persistent local storage and public display (including after subscription/provider changes). The owner approved OpenFootball static CC0 data at €0, with partial coverage and manual completion via 4a (4b). If rights or coverage do not fit, retain manual fixtures and reassess provider scope; do not silently substitute a runtime API dependency or scrape restricted data.

Use a lightweight tiers table and nullable seasons.elche_tier_id. Competition is a fixture fact; Elche's division belongs to its season. No multi-club membership service/table, competition edition model or persisted statistics. Manual tier correction is owner-controlled, not inferred from a cup response.

## Authentication and authorization

Owner-approved choice: **Neon Auth (Managed Better Auth) with Google**, using the official `@neondatabase/auth` Next.js SDK and a small custom Spanish sign-in UI. Google shared credentials are for development/testing only; own credentials/domain setup will be required before production. Current installed SDK is pinned to `0.6.0-beta`; the SDK version is pre-release even though Neon describes the managed service as generally available. Its package includes transitive UI dependencies; the app imports only the API client/server paths, not a UI kit. Reassess the pin on deliberate upgrades.

Alternatives reviewed: Auth.js has an adapter-free session option but its current Next.js setup remains beta; self-managed Better Auth gives more hooks/control but requires owning its server/schema integration. Neon Auth fits the existing Neon environments and removes that maintenance. Local passwords, email delivery services, role systems and signup UI are unnecessary here.

**Authentication is not authorization.** `getVerifiedSession()` obtains a session through the native SDK with `disableCookieCache=true` and `disableRefresh=true`, so protected authorization does not rely on a previously cached session snapshot or attempt session renewal during Server Component rendering. It fails closed on upstream errors/expired sessions. `requireAdmin()` then compares `session.user.id` exactly against the explicitly configured `ADMIN_USER_ID`. The ID is the stable Neon Auth user identity scoped to that branch, not a display name, email, client field or an automatically assigned first user. Unknown/missing owner configuration denies every admin operation. Native Neon roles do not grant application admin rights.

`/auth/sign-in` offers Google login; `/auth/account` shows only the signed-in user's own ID and authorization state, so the owner can configure the allowlist explicitly after the first login. It does not grant access or write configuration. Development and testing can have different user IDs. Use separate `TEST_ADMIN_USER_ID` and test Auth URL/secret for manual testing. Localhost ports share browser cookies: use a separate browser profile/incognito context for manual testing to avoid mixing sessions between environments.

The public footer's owner entry targets `/admin` with prefetch disabled: public browsing does not trigger private session requests until the owner clicks. The protected destination redirects unauthenticated visitors to sign-in. The sign-in page is request-rendered and checks the live session: an authenticated owner proceeds to `/admin`, another authenticated account proceeds to `/auth/account`, and only an unauthenticated visitor sees Google login. This fixes the reported immediate return-to-login screen: previously the footer always linked to a static sign-in page that displayed login even when the session was valid. That screen alone was not evidence of session expiry.

`src/proxy.ts` applies native SDK session middleware to `/admin/:path*` and the OAuth landing page `/auth/account`, for the native verifier exchange, session redirects and cookie maintenance. It is not an authorization boundary. Every protected read and Server Action calls `requireAdmin()` independently before reading PostgreSQL or parsing/writing submitted references. The native `/api/auth/[...path]` handler preserves OAuth/verifier/session handling. Cookies and auth responses are not public cached content; public archive pages remain independent of Auth availability.

ADM-01 diagnosis (2026-10-24): a synthetic upstream that renews the session token reproduces a false “Acceso restringido” with a valid owner session. SDK 0.6.0-beta writes upstream cookies in `getSession()`; Next.js forbids those writes during page rendering, and our error handling correctly denies access on that exception. Additionally, the SDK middleware's local-cache path discards upstream token renewal cookies. The proxy therefore forces its internal session lookup through the SDK's uncached path, with refresh enabled, forwarding renewal cookies to the browser. Internal lookup parameters are restored to their original values in redirects. Protected server reads use the separate non-refreshing live lookup above. This keeps cookie writes in the response-capable proxy while preserving revocation checks. See upstream reports [render-time cookie writes](https://github.com/neondatabase/neon-js/issues/196) and [lost renewal cookies](https://github.com/neondatabase/neon-js/issues/234); reassess this workaround on an SDK upgrade.

No session duration, cache TTL, service configuration or Auth schema is changed. The three-hour goal applies to normal navigation with a valid upstream session, including a return from public pages; public pages do not renew sessions or contact Auth. Automated HTTP tests cover renewal with and without local cache, repeated requests representing reloads/tabs, public navigation, a synthetically aged three-hour session, expiry, revocation, outages and logout. They do not establish a real three-hour browser/OAuth result or identify the affected environment's actual expiry policy; manual acceptance remains required (README).

Milestone 3 reference editing covers clubs/stadiums/competitions/tiers/seasons only. Server validation normalizes optional fields, keeps existing slugs unchanged, retries concurrent slug reservations under SQL uniqueness, requires explicit delete confirmation and prevents deleting Elche even if unreferenced. PostgreSQL RESTRICT prevents deleting used references. Milestone 4a exposes separately authorized fixture and attendance actions; each write runs in a PostgreSQL transaction, locking the parent fixture to serialize attendance changes and deletion. Public reads remain attendance-only.

Managed users/sessions/configuration belong to Neon's `neon_auth` schema, outside our Drizzle schema and synthetic domain seed. Do not introspect/adopt or reset those tables. Branches were configured separately; no production is used. Automated tests create a uniquely named disposable database on the configured testing server, apply real migrations and seed there, then remove only that database. Existing testing records never participate in the suite and are not reset; the testing role needs CREATEDB. HTTP tests receive the same temporary connection. Automated tests use a loopback-only synthetic Auth upstream exercising the real SDK/middleware/actions, not Google or real user accounts. It is test code only; the app has no login bypass. Real Google login/logout/restoration and final owner allowlist are explicit manual acceptance checks, not claimed by simulated tests. See README.

## File storage: club crests now, trip photos after MVP

Owner approved Neon Object Storage on 2026-10-19 after confirming the project is Free and Storage is available in development/testing (Frankfurt). Free includes 5 GB objects and 5 GB/month shared public network transfer; keep €0, no upgrade or paid add-ons. Public delivery/compute also remains subject to Vercel allowances. Production provisioning/release remains unauthorized. Photos remain a separate post-MVP task; the S3 client and environment isolation can be reused, with separate photo validation/privacy rules later.

Next.js Node Route Handler `/api/admin/club-crest` re-verifies Neon Auth + exact ADMIN_USER_ID before parsing the request, requires same-origin POST and bounds the actual multipart stream (not just Content-Length). PNG/JPEG/WebP inputs up to 1,000,000 bytes are decoded with sharp, limited to 16,777,216 pixels and one page, auto-oriented, resized within 512×512 preserving proportions/transparency, and encoded as WebP without metadata. SVG, animation, MIME/content mismatch and invalid data fail before Storage writes. No originals, browser storage credentials, filesystem uploads or direct public uploads.

`public_read` buckets permit anonymous reads and credentialed writes. Use branch-specific credentials/endpoints, plus an explicit `STORAGE_DATABASE_HOST` binding to the active normalized PostgreSQL hostname. `STORAGE_ENVIRONMENT=testing` selects TEST_* credentials for dev:testing; Vercel preview must use testing and production explicitly requires production mode. Local development cannot select production Storage. Buckets and credentials must be scoped to the correct branch; ancestor credentials can access descendants, so do not reuse a root/production credential. No code creates a production bucket. Local CI uses a loopback S3 wire fixture with the real SDK, synthetic credentials and verified owner sessions, never production or a permission bypass.

The public `/media/crests/<club-id>/<version>.webp` handler resolves only a canonical currently referenced key, fetches the validated public origin without credentials/redirects, and sets cache headers for browser/Vercel CDN delivery. No caller-provided host/URL is accepted. Public copies are intentional publications; cached copies can remain available after replacement/deletion (one-day app-route TTL; direct bucket URLs carry a one-year TTL). New keys avoid stale image replacement. Storage failure preserves the map's neutral badge and navigation.

Storage and SQL are not one transaction. Reserve a cleanup intent before PUT; serialize activation with the reservation and club locks, compare the form's expected prior key, and atomically repoint the club plus retire its previous key. Failed/uncertain PUTs retain a one-hour cleanup delay for late remote writes. Failed DB activation after a completed PUT can be reclaimed immediately; an uncertain COMMIT is safe because cleanup checks active references. Club deletion and crest unlink enqueue keys transactionally. Explicit authorized cleanup handles at most ten due objects, checks references again and retains failed deletions for retry. No cron/worker or reliance on S3 lifecycle/versioning (not enforced by Neon). See DATABASE and README.

## Map comparison and recommendation

| Approach | Tradeoff |
| --- | --- |
| Leaflet with raster tiles | Original base; Leaflet still owns markers/popups/touch interaction. |
| MapLibre GL JS with vector tiles | Chosen for Liberty rendering as a Leaflet base layer after MAP-01 review. |
| Custom SVG Spain map | No tile dependency and strong visual control; projection, insets, zoom and interaction become custom work. |
| Google Maps / Mapbox | Capable managed platforms; little benefit without routing/search requirements. |

The original Milestone 5 base (2026-10-18) used Leaflet with standard OSM raster tiles. Owner-approved MAP-01 replacement (2026-10-24): **OpenFreeMap Liberty**, based on OSM/OpenMapTiles, rendered by MapLibre GL JS 5.24.0 through `@maplibre/maplibre-gl-leaflet` 0.1.4 inside the existing Leaflet map. Leaflet continues owning markers, panels, keyboard/touch controls and camera; the vector renderer is noninteractive and uses the tile pane. Imports are client-only; no CDN scripts in the application. This changes the base cartography, not public query semantics or attendance rules.

The [OpenFreeMap public instance](https://openfreemap.org/) requires no account or API key and publishes no usage quotas; it has no SLA and its [terms](https://openfreemap.org/tos/) allow availability changes. Keep the strict €0 budget and visible OpenFreeMap, OpenMapTiles and OSM credits. The browser directly requests the style, tiles, fonts and sprites. No proxy, offline download, account provisioning, paid plan or geocoding. Source/style outages show a status; lack of WebGL or initialization failure preserves server-rendered panels, lists and history links. A partial WebGL setup failure is cleaned up even if the bridge's removal hook cannot run normally. There is no automatic fallback to another provider.

Public server configuration is now `MAP_STYLE_URL` (default `https://tiles.openfreemap.org/styles/liberty`) and `MAP_MAX_ZOOM` (default 19, integer 1–19). Reject non-HTTPS, credentials, query strings and fragments; do not send credentials to the client. Custom styles must retain the same source attribution contract. Old `MAP_TILE_*` settings are ignored, so existing environments automatically use Liberty unless the new setting overrides it. Invalid configuration disables the renderer while retaining the public list. See [style research and previews](MAP_STYLE_OPTIONS.md). Deployment and external environment changes remain separate from this local implementation.

Load the interactive renderer only on the client, passing minimal visited-stadium data from the server. Start with fixed peninsular Spain bounds (35.7, -9.6)–(43.9, 3.4), independent of visited coordinates; subsequent navigation is unrestricted. The map-first home now uses URL-driven stadium/trip panels instead of the initial bottom card carousel. Selecting a marker opens its stadium panel; selecting a located resource reveals the matching marker without recreating Leaflet. Desktop panels are lateral and mobile panels expand upward; see MAP_EXPERIENCE. Honor reduced motion and keyboard controls. The public map uses the full viewport, accepts wheel zoom and provides explicit zoom/reset controls; there is no public page scrolling to pause interaction for. Unlocated stadiums retain server-rendered panel/list links and panel histories. One marker per stadium with visit count and links; any special appearance derives from associated special trips. Owner-approved marker rule (2026-10-19): the crest represents the opponent of attended visits, never stadium ownership. Derive the opponent from each attended fixture relative to Elche; only one distinct known opponent across every visit permits its clubs.crest_object_key. Multiple opponents, any unknown opponent, missing crest reference or unavailable image use the neutral Elche Away badge. No club–stadium association or multiple-crest markers. Admin-uploaded normalized WebP in Neon Object Storage only; preserve image proportions in a fixed badge, with selected border/halo and accessible stadium/opponent labels. Coordinates are manually entered, no geocoding service. Unknown coordinates omit only the marker. Include islands/autonomous cities when visited. Province fills and licensed/simplified boundary datasets are deferred; no PostGIS.

## Static import implementation (4c)

`/admin/import` is protected like every other administrative operation. Parsing/upload, preview and apply each reverify the owner before input processing or database access. JSON supports a root list, `matches`, and `rounds[].matches`, plus paired score arrays or score objects with `ft`/`et`; penalty scores are never selected. Football.TXT supports the inspected date headings, phase headings, both home-score-away and home-v-away-score layouts, extra-time and shootout prefixes. Unsupported lines/shapes fail explicitly rather than silently dropping fixtures. Unknown dates/scores stay null. Football.TXT years follow the explicit heading/date context and January rollover; unusual chronology requires explicit year headings or a reviewed compatible file. No generic free-text scraper is included.

The normalized record/version hashing, confirmation rules and transaction locks are described in DATABASE. Preview data and the uploaded file are returned only to the authorized browser, not persisted as raw payloads. The server signs the reviewed input plus a database snapshot with an HMAC separated by purpose, using the existing server-only Auth cookie secret. Apply verifies it and reauthorizes; a signed review is not a login credential. Changing environments/secrets invalidates previews. Client decisions must regenerate the preview before apply; no new key, external service, job, runtime provider dependency or production provisioning is added.


## Direct acquisition and global review (4c revision)

Owner-approved additions: anonymous access to the two approved GitHub repositories, a fixed commit per repository per check, reference creation proposed before any write, and global approval followed by atomic bounded batches with explicit resume. Only `directImport` after `requireAdmin()` can initiate acquisition. No component render, scheduled task, webhook or worker calls OpenFootball. The advanced upload flow and its reconciliation rules remain available.

`openfootball.ts` constructs HTTPS requests internally to `api.github.com/repos/openfootball/{football.json,espana}` and `raw.githubusercontent.com/openfootball/{football.json,espana}/<fixed-sha>/<known-path>`. No user URL/token, forwarded credentials or redirects are allowed. Catalogs must be complete (not truncated); declared blobs that fail to download are errors, not absence. Time, byte, record and range limits bound the action. JSON is preferred when cataloged; Football.TXT covers known absent JSON variants. Unsupported competitions/phases remain visible gaps. No historical tier or venue is inferred.

The global preview uses virtual UUIDs for proposed references and creates no staging rows in PostgreSQL. Exact unambiguous names or exact historical source hints can propose a local reference; ambiguity remains manual. Signed review state contains only normalized Elche source records, proposed references, frozen choices and a hash of the local state. It has a separate HMAC purpose, expires after 30 minutes and is size-limited. Applying requires server-verified global readiness AND explicit confirmation; an unresolved later batch cannot be bypassed by applying an earlier one.

Each request applies at most 40 fixtures plus references/provenance and an `import_batches` receipt in one transaction. A browser loop is started solely by the owner's confirmation; stopping/closing the page stops new requests. No batch runs automatically after recovery. Receipts plus signed checkpoints handle lost responses without replaying writes. Changes outside the confirmed execution invalidate the next checkpoint. Browser sessionStorage retains the signed review for explicit recovery in that tab/origin; expired/lost reviews require another manual check. All actual archive reads continue using PostgreSQL only. No raw files or draft plans are persisted in PostgreSQL.

Official GitHub references verified during this implementation: [Get a reference](https://docs.github.com/en/rest/git/refs#get-a-reference), [Get a tree and truncation](https://docs.github.com/en/rest/git/trees#get-a-tree). These are public read operations; the application sends no Authorization header.
